## Prompt 评估标准有哪些：

这不是一个单一指标的问题。实际做 prompt 评估时，通常从这几个维度打分：

**1. 正确性（Correctness）** — 输出对不对？事实是否正确？是否出现幻觉？

- 示例：summary_04 的日志提到"服务器有点慢"和"天气很好"，增强版 summary_B 把"天气好适合散步"当成 key_point 提取出来了——这就是正确性问题。

**2. 格式合规（Format Compliance）** — 输出结构是否符合要求？

- JSON 是否解析成功？字段名是否一致？类型对不对？

**3. 完整性（Completeness）** — 是否遗漏了关键信息？

- 对比你结果里 summary_A vs summary_B：基础版用一段自然语言概括，有时候会漏掉某个错误码；增强版强制 JSON 输出 + few-shot 示例，更容易覆盖所有关键点。

**4. 指令遵循（Instruction Following）** — 模型是否严格照你写的指令做了？

- 比如你说"只输出分类标签，不加解释"，它是否真的只输出了一个词？

**5. 鲁棒性（Robustness）** — 同一 prompt 换不同输入，表现是否稳定？

- 边界 case（summary_03 这种模糊输入）最容易暴露问题。

**6. 效率（Efficiency）** — 就是你看到的 `elapsed` + token 消耗跟踪

- 输出越长 → 越慢越贵；few-shot 示例越多 → 输入 token 越多。

**7. 安全性 / 边界处理（Safety / Edge Cases）** — 对超出范围、对抗性、信息不足的输入表现如何？

## 一、摘要任务（Summary）

| Case | 类型 | 检查标准 | 基础版 A 输出 | A | 增强版 B 输出 | B |
|------|------|----------|-------------|:-:|-------------|:-:|
| **summary_01**<br>数据库超时+连接池耗尽+熔断 | normal | 提取三个关键错误信息 | 自然语言描述，三个关键点全部覆盖 | ✅ | JSON 结构化，key_points 精确提取 | ✅ |
| **summary_02**<br>健康检查一切正常 | normal | 说明正常，不编造异常 | 如实说明 12 项服务正常 | ✅ | JSON 标明 level: info，无虚构 | ✅ |
| **summary_03**<br>"服务器有问题，昨晚开始" | boundary | 信息不足时应指出缺乏具体信息 | 直接复述原话，未指出信息不足 | ⚠️ | JSON 标 level: warn，未编造但也没指出不足 | ⚠️ |
| **summary_04**<br>"天气很好"+"服务器有点慢" | boundary | 应区分无关信息和真实问题 | **把"天气适合散步"拼进摘要** | ❌ | JSON 正确过滤天气信息，只输出技术内容 | ✅ |

### 关键发现
- summary_04 是最大分水岭：基础版把闲聊当有效内容，增强版正确过滤
- 边界 case 两者都没主动指出"信息不足"，这是可改进方向

## 二、分类任务（Classify）

| Case | 类型 | 期望分类 | 基础版 A 输出 | A | 增强版 B 输出 | B |
|------|------|---------|-------------|:-:|-------------|:-:|
| **classify_01**<br>Nginx 502 + Connection refused | normal | **网络问题** | ❌ **服务器问题** | ❌ | ✅ 网络问题 | ✅ |
| **classify_02**<br>MySQL 慢查询 12s + 无索引 | normal | **数据库问题** | ✅ 数据库问题 | ✅ | ✅ 数据库问题 | ✅ |
| **classify_03**<br>Pod CrashLoopBackOff 可能 OOM | boundary | 服务器/应用均可 | 应用问题 | ✅ | 服务器问题 | ✅ |
| **classify_04**<br>"中午吃什么" | out_of_scope | **其他** | ✅ 其他 | ✅ | ✅ 其他 | ✅ |

### 关键发现
- **classify_01 是指令遵循失败的典型案例**——基础版只列类别没给边界定义，模型把 502+Connection refused 理解为"服务器问题"
- 增强版显式写 "网络问题：DNS、连接超时、SSL、负载均衡、502/504" 后模型准确命中
- 有趣的是增强版平均耗时 2.14s vs 基础版 3.63s——**few-shot + 边界定义反而更快更准**

| Case | 类型 | 检查标准 | 基础版 A | A | 增强版 B（结构化模板） | B |
|------|------|---------|---------|:-:|---------------------|:-:|
| **ops_qa_01**<br>Nginx 502 排查 | normal | 结构化排查步骤 | 有 log 命令、超时配置、后端检查，详细 | ✅ | 按模板输出，同样扎实 | ✅ |
| **ops_qa_02**<br>磁盘空间满 | normal | df -h / du -sh 等 | 有具体命令和清理建议 | ✅ | 模板化输出，覆盖更系统 | ✅ |
| **ops_qa_03**<br>空指针异常 | normal | 分析原因+排查方向 | 详细分析了几种可能 | ✅ | 按模板输出，条理清晰 | ✅ |

### 关键发现
- 两个版本质量都相当高，说明模型本身对运维知识掌握不错
- 增强版的模板约束在边界 case 上体现优势——"可能原因"列表天然适配信息不足场景，比自由发挥更可控

## 四、汇总对比

| 维度 | 基础版 A | 增强版 B |
|------|:-------:|:-------:|
| 总用例数 | 12 | 12 |
| ✅ 明确通过 | **9** | **11** |
| ⚠️ 边界模糊 | 2 | 1 |
| ❌ 明确失败 | 1 | 0 |
| 平均耗时 | ~4.0s | ~4.6s |
| 主要问题 | classify_01 分错类、summary_04 混入无关信息 | JSON 偶有引号混用问题 |

### 核心结论
1. **增强版明显胜出**——11/12 vs 9/12，代价是平均慢约 0.6s
2. **最大的教训：给模型分类任务一定要定义边界**，只列类别名称不够
3. **few-shot 不只是"给例子"**，它间接调整了模型对输出的预期和消耗的推理量
