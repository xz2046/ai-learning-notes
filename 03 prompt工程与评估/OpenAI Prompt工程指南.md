## 一、Prompt Engineering 基础

### 1.1 什么是 Prompt Engineering

**Prompt Engineering（提示工程）是编写有效指令的过程，目的是让模型稳定地生成符合你要求的内容。**

由于模型生成的输出是非确定性的（non-deterministic），要让输出符合预期既是一门艺术，也是一门科学。但通过一些技巧和最佳实践，可以稳定地获得好结果。

**核心建议：**

- 生产环境**固定模型快照**（如 gpt-4.1-2025-04-14），确保行为一致
- 构建**测试和评估套件**来衡量 prompt 行为，在迭代时监控性能

### 1.2 消息角色与指令遵循

OpenAI API 中有三种消息角色，它们有不同的优先级：

| 角色 | 说明 | 优先级 |
|------|------|--------|
| developer（开发者） | 由应用开发者提供的系统级指令，定义规则、身份、边界 | 最高 |
| user（用户） | 由最终用户输入的具体问题或任务 | 中间 |
| assistant（助手） | 模型生成的回复 | - |

**理解方式：** developer 消息就像编程语言中的**函数定义**（定规则和业务逻辑），user 消息就像**函数参数**（输入数据）。

在 Responses API 中，还可以使用 instructions 参数来提供高层次指令，它的优先级高于 input 参数中的 prompt。

注意：instructions 参数只对当前请求生效。如果通过 previous_response_id 管理对话状态，之前的 instructions 不会保留到后续轮次。

### 1.3 在代码中管理 Prompt

**永远把 prompt 存在代码里，不要用可复用的 prompt 对象。**

理由：代码管理的 prompt 可以使用类型化输入、代码审查、测试和正常的部署流程来改变模型行为。

最佳实践：

- 把 prompt 构建代码放在一个小模块中，紧邻其支持的特性
- 使用带类型的函数参数或 schema 来处理动态值（如客户数据、文件、任务选项）
- 将生成的 instructions 和 input 直接传给 Responses API
- 部署前添加测试用例和评估检查
- 通过部署系统（含功能开关或配置）逐步发布 prompt 变更

### 1.4 使用 Markdown 和 XML 格式化消息

在 developer 和 user 消息中，使用 Markdown 和 XML 标签来帮助模型理解逻辑边界。

典型 developer 消息结构（顺序通常如下）：

1. **身份（Identity）**：描述助手的目的、沟通风格和高层目标
2. **指令（Instructions）**：模型应遵循的规则、应该做什么、绝对不能做什么
3. **示例（Examples）**：提供输入/输出示例（few-shot）
4. **上下文（Context）**：额外信息，如私有数据、专有知识（通常放在 prompt 末尾）

**提示缓存优化：** 把预期会重复使用的内容放在 prompt 的开头，以及 JSON 请求体的前几个参数位置，可以最大化 prompt caching 的收益。

### 1.5 Few-Shot Learning（少样本学习）

**Few-shot learning 是通过在 prompt 中提供少量输入/输出示例来引导模型完成新任务的方法**，无需微调。

关键要点：

- 展示多样的输入范围及其对应输出
- 通常将示例放在 developer 消息中
- 示例越多效果不一定越好，关键是示例的代表性

### 1.6 包含相关上下文（RAG 基础）

给模型提供额外的上下文信息，原因通常有两个：

- 让模型访问**专有数据**或训练数据中没有的信息
- 把模型的回答范围**约束在特定资源**上

这种将额外上下文添加到 prompt 的技术被称为**检索增强生成（RAG）**。实现方式可以是查询向量数据库后把结果文本拼入 prompt，也可以使用 OpenAI 内置的 file search 工具。

### 1.7 理解上下文窗口

模型在每次生成请求中能处理的**最大数据量**被称为上下文窗口（context window），以 token 为单位。

- 不同模型的上下文窗口大小不同（从 100k 到 100 万 tokens）
- 上下文窗口包含：system prompt、user prompt、历史消息、检索到的文档片段、工具调用结果
- 上下文不是越长越好：成本高、响应慢、重点可能被淹没

## 二、GPT-5.5 Prompt 核心理论与实践

### 2.1 核心原则：结果优先

**GPT-5.5 的最佳实践是：用短而结果导向的 prompt，用明确的输出目标和约束条件来描述任务，让模型自己选择解决方案路径。**

描述"目的地"而非"每一步怎么做"：

好的写法：
解决客户的端到端问题。成功的标准是：
- 从可用策略和账户数据中做出资格决策
- 在回复前完成所有允许的操作
- 最终答案包含 completed_actions、customer_message 和 blockers

避免的写法：
先检查 A，再检查 B，然后比较每个字段...再决定调用哪个工具...

**明确的停止条件**：告诉模型什么时候才算完成，而不是无休止地执行。

### 2.2 个性与行为控制

GPT-5.5 的默认风格是高效、直接、任务导向。对于面向客户的产品，需要显式定义：

- **个性（Personality）**：助手听起来怎么样——语气、温度、直接程度
- **协作风格（Collaboration Style）**：助手怎么工作——何时提问、何时假设

### 2.3 前置说明（Preamble）提升感知速度

对于较长或工具密集型的任务，让模型先发送一个简短的前置说明，承认请求并说明第一步。这在流式应用中能显著改善用户体验。

### 2.4 格式化输出

GPT-5.5 在输出格式上高度可控：

- 默认使用通俗的会话格式：短段落、自然过渡
- 仅在有助于理解时使用标题、粗体、列表
- text.verbosity 参数：low 更简洁，medium（默认）适中

### 2.5 基于事实的回答与引用（Grounding）

定义什么内容需要引用支持、什么样的证据才算足够、证据不足时怎么做。

**检索预算（Retrieval Budget）：** 搜索的停止规则。

对于普通 Q&A：一次广泛搜索即可。前几个结果够用就直接回答。仅在关键信息缺失、用户要求穷举、或需要读取特定文档时才再次搜索。

**创意草稿的护栏：** 区分来源支持的事实和创意措辞。

### 2.6 让模型自我检查

给模型提供能验证输出的工具。对编码任务，要求运行单元测试、类型检查、构建检查或冒烟测试。对视觉产出，要求渲染后检查布局和视觉一致性。

### 2.7 建议的 Prompt 结构模板

角色：[1-2 句话定义模型功能、上下文和工作]

个性：[语气、态度和协作风格]
目标：[用户可见的产出]
成功标准：[最终答案前必须满足的条件]
约束：[策略、安全、业务、证据和副作用限制]
输出：[格式、长度和语气要求]
停止规则：[何时重试、降级、弃答、询问或停止]

### 2.8 不同任务类型的 Prompt 策略

| 任务类型 | 关键策略 |
|---------|---------|
| 编码 | 明确角色 + 结构化工具使用 + 充分测试验证 |
| 前端工程 | 指定技术栈（Tailwind/shadcn/ui）+ 设计质量标准 |
| Agent 任务 | 彻底规划后再执行 + 每次工具调用后反思 + TODO 跟踪 |
| Reasoning 模型 | 高层次目标导向，不过度指定细节 |
| GPT 模型 | 精确、显式、步骤化的指令 |

### 2.9 Reasoning 模型 vs GPT 模型

| | Reasoning 模型 | GPT 模型 |
|--|--------------|---------|
| 比喻 | 像高级同事 | 像初级同事 |
| Prompt 风格 | 只需高层次指导 | 需要精确显式的指令 |
| 详细程度 | 信任它自己规划 | 越详细越稳定 |

## 三、GPT-5.4 补充技巧

### 3.1 核心 Prompt 模式

**输出合约（output_contract）：** 显式指定输出格式约束，哪些算输出、哪些不算、顺序如何。

**指令优先级：** 明确不同来源指令的优先级关系。

**默认跟进策略：** 什么时候可以直接执行，什么时候必须请求许可。

### 3.2 引用最佳实践

- 在 prompt 中描述引用格式并给出示例
- 使用 text.format 参数指定引用格式类型
- 要求模型区分"来源支持的"和"模型推测的"内容

### 3.3 使用 apply_patch 和 Shell 工具

GPT-5.1+ 支持 apply_patch（结构化代码编辑）和 shell（命令行执行）两个内置工具，适用于编码和 agent 场景。

## 四、元提示（Metaprompting）

用 prompt 来分析和改进另一个 prompt。两步走：

1. **分析失败原因**：把系统 prompt + 失败案例喂给模型，让它定位冲突或模糊的指令
2. **提出修补方案**：让模型给出精确的修订——清除矛盾、明确优先级、简化模糊表述

## 五、关键总结

### 核心原则清单

1. 用明确的角色和指令定义行为边界
2. 用结构化格式（Markdown + XML）组织 prompt
3. 用 few-shot 示例稳定输出格式
4. 为模型提供相关上下文（RAG）
5. 定义清晰的停止条件和成功标准
6. 用评估驱动改进，不凭感觉
7. 结果优先：描述目标而非步骤
8. 区分个性指令和任务指令
9. 给模型自我验证的工具和规则
10. 用元提示迭代优化 prompt

### 常见误区

- 把 prompt 写在代码之外，难以管理和版本控制
- 错误地认为上下文越长越好
- 一次写完美（应迭代+评估）
- 忽略停止条件（模型可能无休止执行）
- 不明确规则优先级（矛盾时模型不知道该听谁的）
- 把旧模型的冗长 prompt 直接搬给新模型（GPT-5.5 可以用更短的 prompt）
