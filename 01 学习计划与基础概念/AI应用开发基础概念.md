# AI应用开发基础概念

## 1. LLM 是什么

**LLM（大语言模型）本质上是在做“根据已有文本，预测下一个 token”**。

你可以把它理解成一个见过海量文本的“自动续写机器”，但它续写得非常像在理解、推理、总结、翻译、写代码。

- 它不是在数据库里“查标准答案”
- 它也不是像人一样真正理解世界
- 它是通过训练学到大量语言模式，再根据上下文生成最可能的结果

### 为什么它看起来很聪明

因为语言里本来就包含很多规律：什么问题后面常接什么答案；什么错误常对应什么原因；什么代码模式后面常接什么修复方式

所以它能表现出：问答、摘要、分类、翻译、写代码、分析日志、生成 SQL、规划步骤

## 2.Token 是什么

**Token 是模型处理文本时的最小单位，就是模型读和写的“字数成本单位”。**

它不是“一个汉字”也不是“一个单词”，而是模型自己切分出来的片段。

## 3. 上下文窗口是什么

**上下文窗口（context window）就是模型一次最多能看到多少内容。**

这部分内容通常包括：

- system prompt
- user prompt
- 历史聊天记录
- 检索出来的文档片段
- 工具调用结果

#### 为什么重要

因为 AI 应用开发里，很多问题本质上都是：**你到底把哪些信息塞给模型了。**

如果塞太少：模型信息不够，容易瞎猜

如果塞太多：成本高、响应慢、重点被淹没、甚至超过窗口上限

#### 一个很常见的误区

不是上下文越长越好。**上下文长，不等于上下文有效。**

就像你问同事一个问题，结果把 50 页文档全扔给他，不一定更容易答对，反而更乱。

所以后面才会有 **RAG**：不是把所有资料塞进去，而是**只塞最相关的那几段**。

## 4. Prompt 是什么

**Prompt 就是你给模型的输入指令。**

它不只是“问一句话”，而是你如何定义任务。

比如你可以这样写：

```
你是一个运维助手。
请基于给定资料回答问题。
如果资料里没有明确答案，就回答“不确定”。
输出格式：
1. 问题判断
2. 可能原因
3. 排查步骤
4. 风险提示
```

这就是 prompt。

### Prompt 的作用

Prompt 决定：模型扮演什么角色、回答风格是什么、输出格式是什么、不确定时怎么处、是否必须引用资料。

### 为什么 AI 应用里 prompt 很重要

因为很多业务能力，早期不是靠训练，而是靠 **提示词约束** 做出来的。

比如：摘要、分类、信息抽取、结构化输出、故障排查建议

**你可以把 prompt 理解成：给一个很聪明但不会主动猜你意图的同事写任务说明。**说明越清楚，结果越稳定。

## 5. Temperature 是什么

**Temperature 是控制输出“发散程度”的参数。**

简单说：

- **低 temperature**：更稳、更保守、更像标准答案
- **高 temperature**：更发散、更有创造性、更不稳定

#### 什么时候低一点

适合：问答、信息抽取、分类、JSON 输出、运维分析、代码生成

一般业务系统里，通常希望它低一些。

#### 什么时候高一点

适合：文案创作、头脑风暴、故事生成、创意写作

## 6. Embedding 是什么

**Embedding 是把文本变成向量表示。**

向量你可以先理解成一串数字，用来表达“这段文本的语义特征”。

比如这两句话：

- `Nginx 502 如何排查`
- `网关返回 502 错误怎么处理`

虽然字面不完全一样，但语义接近，embedding 后它们在向量空间里会比较近。

### Embedding 有什么用

最核心用途是：

**做相似度检索。**

也就是：

- 用户提一个问题
- 你把问题转成向量
- 去和知识库里所有文档片段的向量比相似度
- 找出最相关的几段

这就是 RAG 的基础。

### 重点

Embedding **不是拿来生成答案的**。它是拿来**找资料**的。

所以你要区分两类模型能力：

- **生成模型**：负责回答
- **Embedding 模型**：负责检索 

## 7. RAG 是什么

**RAG = Retrieval-Augmented Generation，检索增强生成。**

意思是：
模型回答前，先从你的知识库里找相关资料，再结合资料回答。

### 为什么要有 RAG

因为 LLM 本身有几个天然问题：

- 可能不知道你的私有数据、可能不知道最新信息、可能会幻觉、不能可靠记住企业内部文档

RAG 的思路就是：**别只靠模型脑补，让它先“开卷考试”。**

### 基本流程

1. 用户提问
2. 把问题做 embedding
3. 去向量库检索最相关文档片段
4. 把这些片段拼进 prompt
5. 让 LLM 基于这些内容回答

### RAG 的好处

- 可以接企业私有知识、可以接最新文档、能减少幻觉、能给出处和引用

### 但 RAG 不是万能的

RAG 更适合：知识问答、文档问答、FAQ、规章制度查询、操作手册查询

RAG 不适合直接解决：当前 CPU 使用率是多少、某服务现在是否异常、某 IP 现在能不能 ping 通

这些是 **实时状态问题**，应该交给工具调用。

## 8.Tool Calling 是什么

**Tool Calling 就是让模型决定何时调用外部工具或函数。**

模型本身不会真的去查数据库、调监控平台、执行命令。它只能“**判断现在应该调用哪个工具，并组织参数**”。

比如用户问：

> ```
> payment-service 当前状态怎么样？
> ```

模型可能判断：

- 需要调用 `get_service_status("payment-service")`
- 再调用 `get_recent_alerts("payment-service")`

拿到结果后，再组织成自然语言回答。

### Tool Calling 解决什么问题

解决的是 **“模型不能直接获取实时世界信息”** 这个问题。

比如：查服务状态、查告警、查监控指标、查数据库、调工单系统、查 CMDB、查日志平台

## 9.RAG 和 Tool Calling 的区别

RAG查的是**静态知识，Tool Calling查的是动态信息**

一个简单判断方法如果问题是在问：**“应该怎么做，通常偏 RAG；现在发生了什么。通常偏工具调用**

## 10. 什么是幻觉

**幻觉就是模型一本正经地说错话。**

它可能：编造事实、编造引用、编造接口、编造日志原因、编造不存在的配置项

### 为什么会幻觉

因为模型的目标不是“查真相”，而是**生成最像正确答案的文本**。它擅长“像”，不天然保证“真”。

### 怎么降低幻觉

常见办法：

- 用 RAG 提供依据
- 用 prompt 明确要求“不知道就说不知道”
- 限制回答必须基于提供材料
- 用结构化输出约束结果
- 对关键结果做工具校验

### 重点

幻觉不是 bug，它是 LLM 这种机制的自然副作用。所以做 AI 应用，核心不是幻想“完全没有幻觉”，而是**设计系统去约束和兜底**。

## 11. 什么是结构化输出

**结构化输出，就是要求模型按固定格式返回结果。**

比如 JSON

### 为什么重要

因为业务系统不是只给人看，还要给程序处理。

如果模型每次都自由发挥：很难解析、很难做自动化流程、很难做稳定集成

所以 AI 应用里经常要求模型：输出 JSON、输出固定字段、输出 Markdown 模板、输出分类标签

## 12.AI应用开发需建立认知

**第一，LLM 负责生成，不负责保证真实。**
**第二，RAG 负责补知识，Tool Calling 负责补能力。**
**第三，Prompt 决定输出质量和稳定性。**
**第四，AI 应用开发的重点是系统设计，不是训练模型。**

## 13. 整条链路怎么串起来

你这条学习路线，本质是这条主线：

#### 第一层：先学会调用模型

**Python + API** 先让模型能工作。

#### 第二层：学会控制模型

**Prompt + 结构化输出** 让它别乱答。

#### 第三层：给模型外挂知识

**Embedding + RAG** 让它能用你的文档回答。

#### 第四层：给模型外挂能力

**Tool Calling** 让它能查实时状态。

#### 第五层：把这些能力封装成服务

**FastAPI + Docker** 让它能变成真正可用的系统。

## 14. 用运维助手场景把概念串一遍

假设用户问：

> ```
> 订单服务 5xx 升高，怎么排查？
> ```

系统可能这样工作：

#### 第一步：Prompt 定义角色

告诉模型：

- 你是运维助手
- 输出排查步骤
- 不确定要说不确定

#### 第二步：判断需要什么能力

模型判断：

- 需要查运行手册 → RAG
- 需要查当前服务状态和最近告警 → Tool Calling

#### 第三步：RAG 检索

从知识库里找：

- `5xx_runbook.md`
- `order-service_故障手册.md`

#### 第四步：工具调用

调用：

- `get_service_status("order-service")`
- `get_recent_alerts("order-service")`

#### 第五步：LLM 汇总回答

模型根据：

- 用户问题
- 检索结果
- 工具结果

生成最终回答：

- 问题判断
- 可能原因
- 排查步骤
- 风险提示

这就是一个典型 AI 应用。

## 15.AI 应用开发常见架构图

**AI 应用开发的架构，本质是“模型前后各加一圈系统能力”**

当前ai agent流程：

**用户目标 → LLM 规划步骤 → 调工具/查资料/执行命令 → 观察结果 → 再规划 → 继续执行 → 直到完成任务**

### 一个完整 AI 应用通常有哪些层

- #### 第 1 层：输入层

  负责接用户请求：Web、API、聊天界面、命令行
- #### 第 2 层：编排层

  负责判断怎么处理请求： 是直接问 LLM、 还是走 RAG、还是调用工具、 还是进入 agent 流程
- #### 第 3 层：能力层

真正提供能力的地方：LLM、Embedding、检索器、工具调用、 工作流
- #### 第 4 层：数据层

提供知识和状态：文档库、向量库、数据库、日志、监控系统、外部 API
- #### 第 5 层：治理层

保证系统可用：日志、监控、鉴权、限流、评估安全控制

接下来完成目标流程：

**FastAPI 接口层 → 路由判断层 → RAG 检索层 / 工具调用层 → LLM 汇总层 → 返回结果**

##学习疑问与解答：

### 问题1：system prompt，user prompt

#### 两者的区别

##### 1. 作用不同

- **system prompt**：定规则、定身份、定边界
- **user prompt**：提具体问题、提具体任务

##### 2. 稳定性不同

- **system prompt** 一般比较稳定，很多轮都共用
- **user prompt** 每次都会变

##### 3. 优先级不同

通常设计上： **system prompt 的优先级高于 user prompt**

比如 system 里写：

> 不确定就说不知道，不要编造

即使用户说：

> 你直接猜一个也行

一般也应该优先遵守 system 的规则。

-------

### 问题2：所以正常一个LLM模型是包含生成模型和Embedding 模型两个部分吗，这是两个独立的模型，还是底层是同一模型，不同方向使用。

- 通常是两个独立模型

### 衍生：**主流 LLM 产品层面**通常由这些部分组成：

- **生成模型**：负责文本生成与推理

- **Embedding 模型**：负责向量化与检索

- **Tokenizer**：负责文本与 token 互转

- **Context/Prompt 组装层**：负责拼接系统提示、用户输入、历史消息、检索结果、工具结果

- **推理服务层**：负责模型加载、推理、并发、缓存、流式输出

- **安全对齐层**：负责内容安全、拒答策略、行为约束

- **工具调用层**：负责函数调用、外部 API/工具接入

- **检索层**：负责向量检索、重排、召回

- **记忆/会话层**：负责多轮对话历史管理

- **评估与监控层**：负责日志、质量评估、调用监控

## 问题3：当自己的知识库太过片面时，RAG检索是否会有负向优化，如何避免这个问题。是否可以定义RAG检索与回答的关联性强度。

**会，而且很常见。**
当知识库**片面、过时、低质量、覆盖不足**时，RAG 可能比不用 RAG 更差，因为它会把模型强行拉向错误或不完整的上下文。

### 为什么会负向优化

RAG 的前提是：**检索结果比模型自身先验更可靠。**
如果这个前提不成立，就会出问题：

- 检索到了**错误内容**
- 检索到了**局部正确但整体误导**的内容
- 检索结果和问题**关联弱**
- 知识库覆盖不够，模型却被要求“必须基于检索回答”

这样会导致：答案变窄、答案被误导、模型忽略常识和通用知识、明明不知道，却基于烂材料硬答

#### 怎么避免

核心不是“永远用 RAG”，而是**让系统学会判断这次该不该信 RAG、信多少。**

##### 1. 做检索质量门槛

如果召回结果相关性太低，就**不要强行使用**。
可以直接走：通用回答、明确说知识库不足、要求用户补充信息

##### 2. 区分“知识型问题”和“开放型问题”

不是所有问题都适合 RAG。
如果是：企业内部流程、私有文档、runbook适合强依赖 RAG。

如果是：通用原理、开放讨论、常识性解释不一定要强绑 RAG。

##### 3. 给知识库做质量分层

不要把所有文档一视同仁。给文档加权重：

- 官方文档 > 个人笔记
- 新文档 > 旧文档
- runbook > 闲聊记录

##### 4. 让回答显式区分“基于检索”与“基于通用知识”

这样模型不会把两者混在一起说成一个确定结论。

##### 5. 做“无答案”策略

当检索结果不足时，允许模型输出：

- 知识库未覆盖
- 现有资料不足以支持结论
- 以下内容仅为通用经验，不是知识库结论

##### 6. 检索后重排

先召回，再做 rerank，降低低相关片段混进上下文的概率。

##### 7. 控制上下文污染

不要因为检索到一点相关词，就把大段弱相关内容全塞进去。


### 能不能定义 RAG 检索与回答的关联性强度

**可以，而且应该做。**本质上你是在定义一个：**“这次回答有多大程度依赖检索结果”的置信机制。**

常见做法有三层。

##### 第一层：检索相关性强度

看召回结果本身是否靠谱，比如：

- top1/topk 相似度分数
- 分数差距是否明显
- 是否多个 chunk 指向同一结论
- 是否命中元数据过滤条件

##### 第二层：回答可支撑强度

看检索内容是否足以支撑回答，比如：

- 回答中的关键结论能否在检索片段中找到依据
- 是否只是关键词相关，但没有真正答案
- 检索片段之间是否互相冲突

##### 第三层：最终回答依赖强度

可以人为定义回答策略，例如：

- **高依赖**：只允许基于检索内容回答
- **中依赖**：优先基于检索，缺失部分允许补充通用知识
- **低依赖**：检索仅作参考，主要按模型常识回答
- **拒答**：检索太差，不回答具体结论

------

### 最关键的一点

**RAG 不是“检索到了就必须喂给模型并强行回答”，而是“先判断检索值不值得信，再决定回答策略”。**

### 详细做法：

用 **四级分级** 最实用：**A 强关联、B 中关联、C 弱关联、D 无关联/拒答**。
核心不是分得多细，而是**每一级对应明确回答策略**。

建立对应分级的回答模板，在返回json时添加参数确定按那一级去做判断的。

### 问题4：本地部署的llm如何解决训练数据不是最新的问题

**核心靠外挂，不靠重训。**

常见做法：

- **RAG**：接最新文档、知识库、网页、数据库
- **工具调用**：查实时系统、接口、搜索引擎
- **定期增量更新知识库**：重新切块、向量化、建索引
- **微调/继续训练**：只适合补风格或垂直知识，不适合高频追最新
- **混合策略**：静态知识走 RAG，实时数据走工具

一句话：**本地 LLM 本体不最新，就靠“检索最新资料 + 调实时工具”补上。**

### 问题5：那当前的codex、claude code都可以直接执行命令，所以说ai agent是Tool Calling功能的延续对吗。

**对，但不完全等于。AI agent 可以看作是以 Tool Calling 为基础，再往前走了一步。**

简单说：

- **Tool Calling**：模型会选工具
- **Agent**：模型不只会选工具，还会**围绕目标连续决策、执行、观察结果、再调整**

所以 agent 一般比普通 Tool Calling 多这几层：

- **任务拆解**
- **多步执行**
- **状态管理**
- **结果反馈后继续决策**
- **失败重试或换路**

像 codex、claude code 这类能直接读文件、改代码、跑命令、看报错再继续修的，本质上已经不是“一次性调个工具”了，而是：

**模型 + 工具 + 循环决策机制**

所以你的理解可以简化成一句话：

**Agent 是 Tool Calling 的扩展形态，核心区别是“单步调用”升级成了“面向目标的多步闭环执行”。**

### 问题6：Temperature如何去控制

**Temperature 通过改变“选下一个 token 时的概率分布”来控制输出发散度。**

你可以直接理解成：

- **低 Temperature**：更倾向选概率最高的词，回答更稳、更保守
- **高 Temperature**：更容易选次高概率甚至更分散的词，回答更多样、更发散

它控制的不是“内容对不对”，而是**输出有多敢偏离最稳答案**。

常用经验：

- **0 ~ 0.3**：适合问答、分类、抽取、代码、运维分析
- **0.4 ~ 0.7**：适合一般聊天、总结、改写
- **0.8 以上**：适合创意写作、头脑风暴

一句话：**Temperature 越低越像按标准答案答，越高越像自由发挥。**
